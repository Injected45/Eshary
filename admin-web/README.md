# إشاري | ESHARI Admin — منصة الإدارة والتحكم

منصة ويب (Next.js + TypeScript) تُدير تطبيق إشاري من **قاعدة Supabase نفسها** التي يعمل عليها التطبيق: لا قاعدة ثانية ولا نظام هوية ثانٍ، فحالة أي حساب واحدة في التطبيق والمنصة.

> **الحالة:** المرحلة الأولى (MVP) مكتوبة ومُختبرة محليًا (وحدات + قاعدة البيانات). **لم تُنشر بعد** — النشر يحتاج حسابك على Vercel ومفاتيح مشروعك، وهي خارج متناول أي مساعد برمجي. لا يُعتبر الرابط منشورًا إلا بعد تنفيذ «اختبارات ما بعد النشر» أدناه.

## تشغيل سريع على جهازك (بلا أي اشتراك)

الرابط: **http://localhost:8100** (مختلف عن 8000 المستعمل لمشروعك الآخر).

1. نفّذ `supabase/migrations/0077_platform_staff.sql` في SQL Editor (مرة واحدة).
2. ضع مفتاح `service_role` في `admin-web/.env.local` (باقي القيم مكتوبة).
3. شغّل `bootstrap-admin.bat` (مرة واحدة) لإنشاء حسابك الأول.
4. شغّل `run-admin.bat` — يفتح المتصفح على الرابط. أغلق النافذة لإيقافه.

الرابط يعمل ما دام الكمبيوتر شغّالًا وملف التشغيل مفتوحًا؛ لفتحه من هاتفك على نفس الشبكة استعمل عنوان الكمبيوتر (مثل `http://192.168.1.5:8100`).

## 1) ما الذي يعمل فعلًا

| الوظيفة | الحالة |
|---|---|
| دخول: بريد + كلمة مرور، ثم **رمز واتساب** (6 أرقام، 5 دقائق، مرة واحدة، 3 محاولات) | مكتوب ومختبر على مستوى قاعدة البيانات |
| منع تجاوز الرمز: الجلسة لا تعمل في أي دالة إلا بعد نجاح الرمز، **حتى لو استُعمل الـ API مباشرة بكلمة المرور** | مختبر |
| لوحة التحكم (إحصائيات حقيقية من القاعدة) | مكتوب |
| إدارة المستخدمين: بحث، ملف تفصيلي، تمديد التجربة، تأكيد دفع، تفعيل نهائي، إيقاف/إعادة تفعيل، ملاحظات، سجل الحساب | مكتوب؛ الإجراءات تستعمل دوال `admin_*` الموجودة في التطبيق نفسه |
| طلبات التفعيل (موافقة 3/7 أيام، طلب معلومات، رفض) | مكتوب (دوال التطبيق نفسها) |
| مركز الإشعارات (الإشعار العام الظاهر في رأس تقارير PDF) + سجله + إيقافه | مكتوب |
| سجل العمليات الإدارية (للقراءة فقط، لا يُعدَّل ولا يُحذف) | مكتوب |
| الأدوار: مدير رئيسي / مدير التطبيق / دعم فني / مراقب، تُفرض في **القاعدة** على كل طلب | مختبر |
| الحسابات الإدارية: إضافة، تغيير دور، تعطيل فوري يُنهي الجلسات | مكتوب؛ القاعدة مختبرة |
| حالة النظام (قاعدة، ساعة الخادم، واتساب، المجدول، تنبيهات) | مكتوب |
| الإعدادات: مدد التفعيل المقترحة، مدة الجلسة | مكتوب |
| PWA قابل للتثبيت على الهاتف، يتحدّث بدون إعادة تثبيت | مكتوب |

## 2) ما لم يُنفَّذ بعد (بصراحة)

- **الإشعار الفوري (Push) لمستخدم أو مجموعة:** التطبيق لا يحوي Firebase/FCM حاليًا. المتوفر اليوم الإشعار العام الظاهر في رأس ملفات PDF. الجدولة وتتبّع التسليم يأتيان مع Push.
- **الدعم الفني (التذاكر):** لا جدول ولا شاشات تذاكر في التطبيق بعد → المرحلة الثانية. بطاقة «طلبات الدعم» في اللوحة تقول «المرحلة الثانية».
- **«النشطون الآن» وآخر نشاط/إصدار التطبيق:** التطبيق لا يرسل نبضة نشاط. يُعرض «لم يُربط بعد» لا رقم وهمي. (آخر تسجيل دخول متاح.)
- **مراقبة النسخ الاحتياطية وأخطاء التطبيق:** تظهر كـ«غير معروف» حتى يُربط الجمع.
- **تعطيل الدخول الإداري القديم بكلمة المرور فقط:** مدير التطبيق القديم (`is_admin` في `account_licenses`) يبقى يعمل في التطبيق كما كان. الرمز يُطلب من حسابات المنصة. لتشديده لاحقًا: انقل ذلك المدير إلى `platform_staff` وأزل `is_admin` (يتطلب أن يدخل المدير من المنصة لا من التطبيق).
- **استرداد الحساب عند فقدان رقم واتساب:** الإجراء المعتمد الآن يدوي: مدير رئيسي آخر يعدّل الرقم من القاعدة، أو تشغيل `platform_staff_add` من جديد. لا استرداد ذاتي (قرار أمني مقصود حتى تُحدَّد السياسة).
- **كلمات المرور** تُخزَّن بواسطة Supabase Auth (bcrypt) وليس Argon2id؛ هذا مقبول أمنيًا لكنه يخالف النص الحرفي للمتطلب.
- **حدود المعدل:** محاولات الدخول مُحدَّدة في القاعدة (20 لكل عنوان و8 لكل بريد كل 15 دقيقة) إضافة إلى حدود رمز واتساب (60 ث بين الرمزين، 5/ساعة للرقم).
- **واتساب:** يمر عبر **البوابة الحالية** (`wa.rhalla.online`) التي يستعملها التطبيق، وهي **ليست** WhatsApp Business Platform الرسمية. اخترتَ ذلك للبدء. الانتقال للرسمي يعني استبدال دالة `_wa_send` في القاعدة فقط، دون لمس المنصة.

## 3) البنية

```
admin-web/
  src/middleware.ts          حارس كل المسارات + تجديد التوكن
  src/lib/                   session (كوكيز مشفرة)، supabase، auth، errors
  src/app/login, verify      كلمة المرور ثم رمز واتساب
  src/app/(app)/...          اللوحة، المستخدمون، الطلبات، الإشعارات، السجل، الحسابات، النظام، الإعدادات
  public/                    manifest + sw.js + أيقونات (PWA)
  scripts/bootstrap-super-admin.mjs   إنشاء أول مدير رئيسي (مرة واحدة)
  tests/                     اختبارات الأمان (vitest)
supabase/migrations/0077_platform_staff.sql   كل ما تحتاجه المنصة في القاعدة
supabase/tests/platform77_test.mjs            اختبار القاعدة (PGlite) — 75 فحصًا
```

### كيف يُفرض الرمز (الفكرة المركزية)
1. كلمة المرور تُتحقَّق عبر Supabase Auth فينتج JWT له `session_id`.
2. الخادم يُرسل رمز واتساب ويحفظ التوكن في كوكي **pending** مشفرة (لا تفتح أي صفحة).
3. الرمز الصحيح فقط يكتب صفًا في `platform_sessions` لهذا الـ `session_id`.
4. الدالة `_platform_role()` لا تُجيب بدور إلا مع صف حي، و`is_caller_admin()` تعتمد عليها لحسابات المنصة. لذلك لا تعمل أي دالة إدارية بكلمة المرور وحدها حتى من خارج المتصفح.

## 4) قاعدة البيانات (ملخص `0077`)

| الجدول | الغرض |
|---|---|
| `platform_staff` | الموظفون: الدور، رقم واتساب (E.164)، التوثيق، فعّال/معطّل |
| `platform_sessions` | جلسات تحقق الرمز (مفتاحها `session_id` للـ JWT) وانتهاؤها وإلغاؤها |
| `platform_settings` | مدد التفعيل المقترحة، مدة الجلسة، تنبيه الانتهاء |
| `wa_challenges` (موجود) | رموز واتساب مخزنة كـ HMAC؛ أُضيف الغرض `platform_login` |
| `audit_log` (موجود) | سجل غير قابل للتعديل؛ يسجل دخول المنصة ومحاولاته |

الدوال: خدمة فقط (`service_role`): `platform_login_start/verify/rejected`, `platform_staff_lookup/add`, `platform_throttle`.
للمصادَقين (وكلها تتطلب جلسة موثقة + الدور): `platform_me`, `platform_logout`, `platform_dashboard`, `platform_users_list`, `platform_user_detail`, `platform_user_set_notes`, `platform_audit_list`, `platform_system_status`, `platform_staff_list/set`, `platform_notifications_list`, `platform_notification_create/set_active`, `platform_settings_get`, `platform_setting_set`.

## 5) الإعداد خطوة بخطوة

1. **القاعدة:** افتح Supabase → SQL Editor ونفّذ `supabase/migrations/0077_platform_staff.sql` (ملف واحد، من نسخ كتلة الـ SQL فقط).
2. **المتغيرات** (Vercel → Settings → Environment Variables؛ لا تُضع أيًّا منها في الكود):

   | المتغير | القيمة |
   |---|---|
   | `SUPABASE_URL` | رابط مشروعك |
   | `SUPABASE_ANON_KEY` | مفتاح anon |
   | `SUPABASE_SERVICE_ROLE_KEY` | مفتاح service_role — **سري، خادم فقط** |
   | `SESSION_SECRET` | 32+ حرفًا عشوائيًا: `node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"` |

3. **أول مدير رئيسي** (مرة واحدة، من جهازك):
   ```bash
   cd admin-web && npm install
   BOOTSTRAP_EMAIL=... BOOTSTRAP_NAME="..." BOOTSTRAP_PHONE=+218912345678 \
   BOOTSTRAP_PASSWORD='كلمة-مرور-طويلة-فريدة' \
   SUPABASE_URL=... SUPABASE_SERVICE_ROLE_KEY=... npm run bootstrap
   ```
   لا حساب افتراضي ولا كلمة مرور ثابتة. يرفض السكربت العمل إن وُجد مدير رئيسي. إثبات ملكية الرقم يحدث عند أول دخول (الرمز يصل إلى الرقم المكتوب).
4. **النشر:** `npm i -g vercel` ثم داخل `admin-web`: `vercel` (ربط المشروع) ثم `vercel --prod`. أضف نطاقك من Vercel → Domains؛ الشهادة (SSL) تلقائية.
5. **تجربة محلية:** انسخ `.env.example` إلى `.env.local` ثم `npm run dev` (المنفذ 3100).

## 6) التحديث والرجوع

- كل `vercel --prod` ينشر على **الرابط نفسه**؛ الاختصار على الهاتف لا يُحذف (الـ service worker لا يخزّن صفحات).
- الرجوع: Vercel → Deployments → اختر نسخة سابقة → Promote to Production.
- بيئة اختبار: أي فرع/`vercel` بدون `--prod` يعطي رابط معاينة منفصل. استعمل مشروع Supabase للاختبار بمتغيرات منفصلة.
- تغييرات القاعدة: ملفات `supabase/migrations` برقم جديد، تُنفَّذ واحدًا واحدًا. لا تحذف جداول `platform_*` عند التحديث.
- الجلسات تبقى بعد التحديث؛ تُنهى فقط إن غيّرت `SESSION_SECRET`.

## 7) النسخ الاحتياطي

القاعدة نفسها هي مصدر البيانات: نسخ Supabase اليومية (Dashboard → Database → Backups) + نسخ التطبيق اليومية. المنصة لا تخزن بيانات خارج القاعدة. للاستعادة تجريبيًا: أنشئ مشروعًا جديدًا، استعد النسخة، ووجّه متغيرات `SUPABASE_*` إليه في بيئة المعاينة، ثم افتح المنصة وتحقق من ظهور المستخدمين.

## 8) الاختبارات المنفذة

```bash
cd admin-web && npm test            # 13 فحصًا: الكوكيز، حراسة كل إجراء، عدم تسريب المفاتيح، رؤوس الأمان
npx tsc --noEmit && npx next build  # يمران
cd ../supabase/tests && npm i && node platform77_test.mjs   # 75 فحصًا على القاعدة
```

اختبار القاعدة يثبت: لا تجاوز للرمز (كلمة المرور وحدها لا تفتح شيئًا)، رمز خاطئ/مستعمل/منتهٍ يُرفض، 3 محاولات تلغي الرمز، الجلسة مرتبطة بـ `session_id` ولا تنتقل لجلسة أخرى، الانتهاء والخروج، كل دور يرى ما يخصه فقط، المشاهد لا يوقف حسابًا، تعطيل موظف يقطع جلساته فورًا، السجل لا يُعدَّل، ودوال الخدمة مغلقة على `authenticated`، وبقاء كل أغراض رموز واتساب السابقة صالحة.

### اختبارات ما بعد النشر (لم تُنفَّذ بعد — تحتاج نشرًا ومفاتيح حقيقية)
- فتح الرابط من الكمبيوتر والهاتف.
- وصول رمز واتساب حقيقي، وقبوله مرة واحدة فقط.
- تفعيل/إيقاف مستخدم حقيقي والتأكد من أثره داخل التطبيق.
- تثبيت PWA على الهاتف، ثم نشر تحديث تجريبي والتأكد من وصوله على الرابط نفسه.
- إرسال إشعار حقيقي لجهاز: **غير ممكن حاليًا** (لا Push في التطبيق).

## 9) ملاحظات أمنية معروفة

- تحذيرات `npm audit` الحالية تخص `postcss` داخل Next 15 (معالجة CSS وقت البناء فقط، لا تمس طلبات المستخدمين). الترقية إلى Next 16 تعالجها وتُجرى في دفعة منفصلة.
- مفتاح `service_role` يستعمله الخادم فقط في: خطوتي الرمز، إنشاء حساب إداري، إنهاء جلسة. اختبار آلي يمنع أي استعمال آخر أو ظهور `NEXT_PUBLIC_`.
- رؤوس الأمان: CSP صارمة (`connect-src 'self'` لأن المتصفح لا يكلّم Supabase)، HSTS، منع الإطارات، `no-store`.
